Cryptography and Network Security · QR authentication

A QR pass that cannot be photocopied.

Colleges use QR codes for attendance and event entry. A QR code is only a picture, so anyone can screenshot it, forward it or edit it. SealPass puts two cryptographic locks on every code. A digital signature proves the college issued it and nobody changed it. A rotating HMAC tag proves it is being shown live, by the phone it was issued to.

01

Why plain QR codes fail

One student, six entries

A typical college QR just encodes a roll number or a fixed token. The scanner reads it and checks it against a list. Nothing in the code proves where it came from or when it was made.

So a student can send a photo of their code to five friends and all six get marked present. Anyone with a free QR generator can make a code for a roll number that is not theirs. Someone can change the event name inside a code and walk into a different event. The scanner cannot tell an original from a copy, because the copy has exactly the same bits.

Hiding the content does not help either. An encrypted code copied pixel for pixel still decrypts. What we need is a code that is bound to its issuer, bound to a moment in time, and usable once.

      Why size decides the signature

      Why Schnorr rather than DSA/ECDSA

      Simpler algebra

      Signing is s = k + e·x, a single linear equation. ECDSA needs a modular inverse of k in every signature. That is fewer operations and fewer places for an implementation to go wrong.

      Provable security

      Schnorr has a security proof that reduces forgery to solving the discrete logarithm problem (in the random oracle model). ECDSA has no comparable clean proof.

      Same compact size

      64 bytes, the same as ECDSA on P-256. We also derive the nonce from HMAC, so a weak random number generator can never leak the key. Chapter 09 shows what happens when a nonce repeats.

      Algorithm studio · Unit 3

      SHA-256, the fingerprint inside everything

      SealPass uses SHA-256 in four places: inside HMAC, to compute the Schnorr challenge e, to derive the signing nonce, and to link the attendance ledger. It turns any input into 256 bits. The output is one-way (you cannot go back from it), collision resistant (you cannot find two inputs with the same output), and it has the avalanche property: flip one input bit and about half the output bits flip.

      1. Pad. Append a single 1 bit, then zeros, then the message length as 64 bits, so the total is a multiple of 512 bits.
      2. Schedule. Each 512-bit block becomes 16 words, which are expanded to 64 words W0..W63 using rotations and shifts.
      3. Compress. Eight registers a..h start from fixed constants (from the square roots of primes). Each of 64 rounds mixes in one Wt and one constant Kt (from the cube roots of primes) using Ch, Maj and the Σ functions.
      4. Add. The registers are added to the starting state. After the last block, the eight words joined together are the digest.

      This is why changing one character of a roll number inside a signed pass is caught immediately: the hash that was signed and the hash of the edited body have almost nothing in common.

      07

      Algorithm studio · Unit 3

      HMAC, the tag that expires every ten seconds

      A plain hash has no key, so anyone can recompute it. A MAC mixes in a secret key, so only key holders can make or check it. HMAC builds a MAC from a hash function using two passes. The nested structure blocks the length-extension attack that a naive H(key || message) allows.

      HMAC(K, m) = H( (K′ ⊕ opad) ‖ H( (K′ ⊕ ipad) ‖ m ) )

      Here ipad is the byte 0x36 repeated, opad is 0x5C repeated, and K′ is the key padded to 64 bytes. SealPass computes:

      tag = first 16 bytes of HMAC( Kse, pass_id ‖ ⌊time / 10⌋ )

      The phone holds Kse, a key unique to this student and this event. Every ten seconds the time slot changes, so the tag changes and the QR redraws. The gate recomputes the tag from its own clock and accepts only the current slot or one either side. A screenshot dies after about 20 seconds. Editing the slot number does not help, because the tag would then be wrong.

      Algorithm studio · Unit 2

      Elliptic curves: a group made of points

      An elliptic curve over a prime field is the set of points (x, y) with y² = x³ + ax + b mod p, plus a "point at infinity" O. Points can be added. Draw the line through P and Q, find where it meets the curve a third time, and reflect that point across the x-axis. Adding a point to itself uses the tangent line instead.

      λ = (y2 − y1) / (x2 − x1)   or   (3x1² + a) / 2y1    x3 = λ² − x1 − x2    y3 = λ(x1 − x3) − y1

      "Division" means multiplying by an inverse mod p, found with Fermat's little theorem. Scalar multiplication kP = P + P + ... + P is fast using double-and-add, about 2·log2k steps. Going backwards, from kP to k, is the elliptic-curve discrete logarithm problem. Nobody knows how to solve it on a 256-bit curve.

      On the right is the toy curve y² = x³ + 3x + 2 over F97. It has 103 points, and 103 is prime, so every point generates the whole group. Click two points to add them. P-256 works the same way, with p ≈ 2256.

      Algorithm studio · Unit 3 · the main algorithm

      The Schnorr signature, step by step

      The Pass Authority has a private key x, a random number below the group order n, and a public key P = xG. P is published inside an X.509 certificate signed by the Campus Root CA.

      Sign

      k = HMAC(x, H(m)) mod n   the nonce
      R = kG
      e = H(R ‖ P ‖ m) mod n   the challenge
      s = k + e·x mod n
      signature = (e, s), 64 bytes

      Verify

      R′ = sG − eP
      accept if H(R′ ‖ P ‖ m) mod n = e

      Why it works

      sG − eP = (k + ex)G − e(xG) = kG = R. Without x, nobody can produce an s that makes this equation work for a new message. That would require solving the discrete logarithm.

      The message m is the whole 40-byte pass body: version, key id, pass id, validity window, roll number and event. Changing any byte changes e.

      Try it

      The nonce must never repeat

      If the same k signs two different messages, then s1 − s2 = (e1 − e2)·x, and anyone can solve for the private key. In 2010 this broke the signing key of a major games console, because its code reused one nonce. SealPass computes k = HMAC(x, H(m)): different messages always get different nonces, and no random number generator is involved.

      Under the hood · Unit 2

      The number theory that holds it up

      Fermat's little theorem

      For prime p and a not divisible by p, ap−1 ≡ 1 (mod p). So ap−2 is the inverse of a. Every point addition uses this to divide.

      −1 mod

      Miller-Rabin primality test

      The curve only works if p is prime. Write p−1 = 2s·d. A random base a either gives ad ≡ ±1, or reaches −1 by repeated squaring. A composite number survives each round with probability at most 1/4.

      Discrete logarithm

      Given P = xG, find x. On the toy curve, trying every value takes at most 103 steps. On P-256 the best known attack (Pollard's rho) needs about 2128 steps.

      Key management · Units 3 and 4

      Key hierarchy, X.509 and TLS

      Symmetric key distribution

      The gate has to check every student's HMAC tag, but storing a key per student on every scanner is fragile. Instead, keys are derived one level at a time with HMAC. A gate gets only the key for its own event and re-derives each student key when it scans. Click "Steal a gate" to see how far one stolen device reaches.

      Public key infrastructure

      How does a gate know which public key belongs to the real Pass Authority? An X.509 certificate, signed by a Campus Root CA whose certificate is built into ("pinned in") every gate. We generated it with OpenSSL (pki/make_pki.sh). The gate checks the root's signature on the certificate, its validity dates and its key usage before it trusts any pass.

      HTTPS during enrolment and gate set-up

      1 · Handshake

      The phone and server agree a fresh session key using ECDHE, which is Diffie-Hellman key exchange on an elliptic curve. A recorded session cannot be decrypted later, even if the server key leaks (forward secrecy).

      2 · Authenticate

      The server presents its X.509 certificate, issued by the same Campus Root CA. The browser checks the signature and the IP address in subjectAltName, which defeats a man-in-the-middle.

      3 · Protect

      Records are encrypted and authenticated with AES-GCM. Kse and Kevent only ever travel inside this channel. The QR itself carries no secret.

      Practical implementation Rubric 5

      Built from first principles, checked against the standards

      We wrote SHA-256, HMAC, the P-256 curve arithmetic and Schnorr ourselves in Python, so every step in this page is code you can read.       Honest limits
      What cryptography alone cannot stop
      
  
      
  
      
    
      Lending the whole phone
      If a student hands over their unlocked phone, the friend holds the real key. No code can tell the two people apart. Mitigation: the gate screen shows the holder's name and roll number for a visual check, and enrolment can be tied to the device.
      
    
      Live relay
      A friend at home can stream a live code to someone at the gate within 20 seconds. One-time use lets only one entry through, and the real student's later attempt is flagged with the time and gate of the first entry. Shorter slots narrow this further.
      
    
      Clock drift
      The phone corrects its clock against the server at enrolment, and the gate accepts one slot either side. A phone that is badly wrong and offline will fail the freshness check. That fails safe: an honest student is asked to reopen the pass, and no cheater gets in.
